# ADR-0011: Versioned idempotent commands

## Status

Accepted

## Date

2026-07-24

## Context

Real-time play over the public internet produces races and repeats as a matter of course:

- A client submits a move based on a board state that the server has already advanced (for example
  the opponent's move arrived while the local player was deciding, or a timeout settled the match).
- A socket drops after the server committed a move but before the acknowledgement arrived. The
  client cannot tell whether its move was applied.
- A client retries a command, or a user double-taps, and the same intent reaches the server twice.

Two of the product's non-negotiable guarantees are directly at stake: zero accepted illegal moves
and zero duplicate rating applications. Both fail if a command can be applied against unexpected
state or applied twice.

Because state is persisted per accepted command with a monotonic version (see
[ADR-0010](0010-match-event-persistence.md)), there is a natural concurrency token available, and
the transaction that applies a command is the natural place to enforce uniqueness.

Status: planned (Phase 2). No command runtime exists today.

## Decision

Every state-changing real-time command carries a version expectation and a client-generated
identifier, and is applied at most once.

- Envelope: `{ commandId, matchId, expectedVersion, sentAtClient, payload }`. `commandId` is a UUID
  generated by the client and reused unchanged on every retry of the same intent. `sentAtClient` is
  diagnostic only.
- Acknowledgement: `{ ok: true, commandId, newVersion }` on success, or
  `{ ok: false, commandId, reason, snapshot? }` on rejection.
- Reason codes are a closed enum: `stale-version`, `not-your-turn`, `illegal-move`, `match-ended`,
  `not-authorized`, `clock-expired`, `duplicate-command`. Clients must handle every member.
- Optimistic concurrency: inside the transaction the server compares `expectedVersion` with the
  stored `version` on the locked match row. A mismatch yields `stale-version` and no state change.
- Exactly-once application: `(match_id, command_id)` is unique. A repeat arrival is not applied
  again; the server responds with `duplicate-command` and attaches the current snapshot, which
  already contains the effect of the original command.
- Rejections that indicate the client's view is out of date (`stale-version`, `not-your-turn`,
  `illegal-move`, `match-ended`, `clock-expired`, `duplicate-command`) carry a snapshot so the
  client can resynchronise in one round trip.
- Clients keep at most one in-flight command per match, never regenerate `commandId` on retry,
  never treat an optimistic overlay as truth, and fall back to `match:sync` after exhausting the
  retry budget.
- A rejection is a normal outcome, not a transport error. `error:recoverable` and `error:fatal` are
  reserved for session and infrastructure failures.

## Consequences

### Positive

- Retries are safe by construction, which is what makes an unreliable connection tolerable: the
  client can always retry the same envelope.
- A lost acknowledgement resolves deterministically. Either the retry returns
  `duplicate-command` with the current snapshot, or `match:sync` shows the move already applied.
- Duplicate rating application is impossible for the command that completes a match, because the
  second arrival never applies.
- Stale clients cannot overwrite newer state, so a slow or backgrounded tab cannot corrupt a match.
- Typed reason codes make client handling exhaustive and reviewable, and they make rejection
  metrics meaningful (a spike in `stale-version` is a specific, diagnosable signal).

### Negative

- Every client that sends commands must implement identifier generation, retry discipline and
  handling for all seven reason codes. That is real client complexity.
- `stale-version` is not automatically retried, so a legitimate but slightly late move must be
  re-decided by the player after resynchronisation, which can feel abrupt.
- Command identifiers must be stored to enforce uniqueness, adding a row lookup per command and a
  table that grows with play.
- Attaching a snapshot to rejections increases payload size on the failure path.

### Neutral

- Non-mutating requests (for example `match:sync`) do not need the envelope, since they change no
  state.
- Adding a new command means extending the schemas in `@gobblet/protocol` and following the
  checklist in [`../protocol.md`](../protocol.md).
- The version counter is per match and is only meaningful within that match.

## Alternatives considered

### Server-generated command identifiers

Rejected because the client needs the identifier before it sends, precisely so a retry can reuse
it. A server-generated identifier cannot deduplicate the request that never received a response.

### Last-write-wins with no version expectation

Rejected because it permits a stale client to apply a move against state it never saw, which can
produce a move that is legal in the client's old state and wrong in the current one. That directly
violates the zero-illegal-moves guarantee.

### Pessimistic locking with client-held turn leases

Rejected as heavier and worse under failure. A lease adds lifetime management, renewal and orphan
recovery, and a client that disconnects while holding a lease creates a new problem. A row lock held
only for the duration of the transaction is simpler and sufficient.

### Sequence numbers per client connection instead of per match versions

Rejected because the meaningful ordering is per match, not per connection. Reconnecting to a new
socket must not reset or reorder anything, and two participants act on the same version line.

### Treating duplicate submission as an error

Rejected because the client cannot always know whether its first attempt succeeded. Returning
`duplicate-command` with the current snapshot turns an ambiguous failure into a clear, actionable
result.
